# 星座控制面失效期间的业务转发

在提供的通用仿真内核上实现一个可执行的双策略对照实验。输入目录 `inputs/` 提供固定设备、定时和业务参数以及用户部署与配对函数。输入中的轨道与物理参数作为只读合同。允许新增场景、协议栈、控制面、路由行为和记录模块。使用模拟时钟对齐事件。

1. 部署倾角 53°、高度 1150 km 的 16×25 星座和两组各 100 名用户。用指定种子实例化站点坐标。每对用户双向在端口 18080 发送 1200 字节报文，自第 5 秒起按配置错峰，每个方向每 2 秒一个。分配能贯穿全链路的唯一消息 ID。
2. 第 105 秒永久停用 377 号卫星。集中式控制器在 0、50、100、150 秒发布网络级路由版本，失效后的下一次发布必须反映新拓扑。在各跳使用当前发布的版本；路由缓存命中时核对表项版本并淘汰过期项。
3. 分布式策略在可用时使用原最少跳数下一跳。遇到失效邻居时仅利用本地可用邻居及路径历史选取绕行下一跳，防止转发循环。保持原有接入和动态物理链路模型。
4. 提交支持 `--routing-mode centralized|distributed --seed N --headless` 的入口。每种模式运行 200 秒。输出 UTF-8 CSV 事件流，含 `event_type,simulation_time,message_id,pair_id,direction,source_user_id,target_user_id,hop_count,path_satellite_ids,note`。事件包括 generate、arrival、satellite_failure；方向为 A_to_B 或 B_to_A。保留逐跳路径与接收端实测，重复到达按 ID 去重。
5. 验证两模式的设备、坐标、业务负载、故障时刻一致。按发包时刻归入 [0,105)、[105,150)、[150,200) 三个窗口，计算交付数、交付率和成功包平均跳数。提交原始事件、路由版本记录与种子参数，并解释故障窗口的交付及绕行开销，以及刷新后的恢复。

输入工程自带通用路由、终端、物理层与场景控制器。工程工作包括连接这些组件并实现两种策略、故障变更和协议栈观测。实验比较以相同时间窗、业务配对与原始事件为依据。
